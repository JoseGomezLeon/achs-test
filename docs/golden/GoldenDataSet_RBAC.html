Referencia: qué debe traer un buen caso de Golden Dataset RBAC

    
Un caso del Golden RBAC no es solo "este rol puede hacer esta acción". Debe permitir que seguridad, QA, arquitectura y auditoría entiendan qué situación de autorización se valida, con qué datos, bajo qué regla del dominio, cuál es el resultado correcto y quién lo aprueba.

    
Cada caso debería tener:

    
    
      
  • Escenario de negocio: qué situación real de autorización representa.
    • 
      
  • Datos de entrada: subject, rol(es), capability requerida, tipo de credencial (sesión BFF o Bearer), endpoint.
    • 
      
  • Resultado esperado: PERMITIDO o RECHAZADO, HTTP status, error_code estable si aplica.
    • 
      
  • Fundamento: ADR que respalda la decisión, regla del capability-map, contrato de error_codes.
    • 
      
  • Criterio negativo: cuándo el sistema debe devolver access_denied, unauthenticated o relation_violation.
    • 
      
  • Tolerancia: el error_code debe ser exacto (estable), no texto libre.
    • 
      
  • Responsable: persona o área que firma que el caso es correcto.
    • 
      
  • Estado: aprobado, pendiente, bloqueado por gap o fuera de alcance.
    • 
    

    
Regla práctica: si un caso solo dice "rol X puede hacer Y", pero no especifica el error_code esperado en el caso negativo, el endpoint afectado y el fundamento del ADR, todavía no debería considerarse Golden oficial.

Glosario de datos, siglas y reglas RBAC

    

      
TérminoDefinición operativa

      
        
RBAC (Role-Based Access Control)Modelo de control de acceso donde los permisos se asignan a roles y los roles a subjects. El módulo controla qué Subject puede ejercer qué Capability.

        
SubjectEntidad autenticada (persona o agente) que solicita acceso. Se construye a partir de los claims del token vía claimsToSubject.

        
CapabilityPermiso granular que un Subject puede tener. Ejemplos: rbac.roles.assign, rbac.audit.view, rbac.simulator.run. Es el contrato público del módulo.

        
AccessContextEstructura inmutable que describe las capabilities efectivas de un Subject en un momento dado. Construida por buildAccessContext a partir de los roles resueltos.

        
capability-mapTabla que mapea cada rol a su conjunto de capabilities. Define la política de autorización. Cambiar el capability-map es una decisión de negocio y requiere ADR.

        
IamAdapterInterfaz que consulta Entra ID para obtener los grupos del Subject. En tests, se reemplaza por StubIamAdapter via IoC con TEST_MODE=architecture.

        
StubIamAdapterImplementación de IamAdapter para tests. Retorna grupos ficticios sin consultar Entra ID. Se registra en el IoC cuando TEST_MODE=architecture.

        
AppAuditWriterInterfaz que registra eventos de decisión de autorización (quién, qué, resultado). No es bloqueante: su indisponibilidad no debe bloquear el acceso.

        
AuthorizationServiceServicio central del dominio RBAC. Expone authz.require(capability) que lanza excepción de dominio si el Subject no tiene la capability.

        
AgentRegistryRegistro de agentes (jobs batch, AFK, HITL, sistemas externos) autorizados a consumir el módulo vía Bearer. Separado de los usuarios humanos.

        
AdminRBACRol propuesto con todas las capabilities de gobierno: assign, revoke, matrix.view, my-access.view, simulator.run, audit.view. Pendiente de validación.

        
AuditorRol propuesto con capabilities de solo lectura: audit.view, matrix.view. No puede modificar roles. Pendiente de validación.

        
OperadorRol propuesto con capability mínima: my-access.view. Solo puede ver su propio AccessContext. Pendiente de validación.

        
SimuladorRol propuesto con capability: simulator.run + my-access.view. Puede simular AccessContext de otros subjects sin modificarlos. Pendiente de validación.

        
access_deniederror_code estable que el módulo devuelve cuando el Subject está autenticado pero no tiene la capability requerida. HTTP 403.

        
unauthenticatederror_code estable cuando no hay credencial válida (token ausente, malformado o expirado). HTTP 401.

        
relation_violationerror_code estable cuando el Subject intenta asignar un rol o capability superior al suyo propio. HTTP 403. Contrato definido en ADR-010.

        
Entra IDProveedor de identidad corporativo de ACHS. Provee los grupos del usuario vía OIDC claims. El IamAdapter los transforma en roles RBAC.

        
Bearer (Client Credentials)Flujo OAuth 2.0 para agentes y sistemas externos. El token Bearer se valida por el mismo pipeline que la sesión BFF — no hay camino privilegiado.

        
TEST_MODE=architectureVariable de entorno que activa el StubIamAdapter y StubAuditWriter via IoC. Permite tests unitarios sin depender de Entra ID ni del sistema de auditoría real.

        
ToxiproxyProxy de red para tests de resiliencia. Simula timeouts, latencia y cortes en la conexión a IamAdapter o AppAuditWriter en tests de Nivel 2.

      
    

  







⚠ Roles y capabilities son propuesta técnica basada en ADR-010. Requieren validación de Arquitectura y Seguridad antes de implementar. Casos marcados GAP no deben implementarse hasta cerrar la definición indicada.
